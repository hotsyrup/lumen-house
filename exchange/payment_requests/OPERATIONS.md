# Provisioning and launch review

Nothing in this change installs a runner, provisions credentials/permissions, changes production policy, migrates live data, supplies funds, deploys or activates a route. Keep the existing no-expiry intake and financial gates. The schema13 host adapter remains a separate private review artifact; publishing private native source is unnecessary and prohibited by this workflow.

## Required ordered approvals

1. Independently review the exact public commit and private native patch/tree. Confirm the actual production native source and stores, current no-expiry intake release and the three existing Durable Object exports/bindings. Approve an isolated staging/provisioning procedure separately. The public Worker remains disabled passthrough.
2. Select one exact existing owner and tenant, intended participants and explicitly scoped permissions. Non-cash resources, limits, retention/dispute policy and grants still need owner definition. The payment principal ceilings above are already approved; they do not approve native financial policies, fees, token configuration or credentials.
3. Approve backup/checkpoint custody, complete copy inventory, retention/deletion process and maintenance cadence. Quiesce the native writer using its supported procedure, verify a private backup and independently pinned checkpoint, rehearse the exact review artifacts on disposable copies, then separately approve explicit schema11→12 and12→13 provisioning. Both extensions create no membership, grant, request, standing authority or payment policy. Reject missing/unknown/altered schemas. Preserve the separate intake database and all its rows.
4. Review real artifact access and independent payee/wallet verification, canonical chain/token tuple and the supported mobile owner confirmation flow. The current flow is missing: there is no enabled wallet button, send integration, or settlement adapter. Fees need exact separate owner confirmation. A future adapter must reconcile uncertain sends without releasing holds or preparing replacements. No standing signing/broadcast authority is acceptable for this request lane.
5. Only after those gaps are addressed, approve a bounded staging acceptance test with the actual deployed identity/tenant, source/evidence, storage, stop, revocation, backup/restore and wallet confirmation boundaries. Offline green tests do not satisfy this step. Then approve the exact deployment and request-preparation enablement separately, observing default STOP. Financial execution remains disabled. A request-only pilot could stop at reviewable drafts, with that limitation explicitly accepted.

No production values are inferred from fixtures. Do not reinterpret native UTC owner-policy intervals as LA days. The LA request overlay is independent and conservative: every unresolved hold counts on every day until a separately reviewed reconciliation design can prove resolution. Default quota exhaustion is a hold, not permission to rotate tenants, reset budgets, reduce fees or pay by another path.

Because this slice has no settlement/release mechanism, 1 USDC of unresolved requests exhausts preparation even on a later day. The 5 USDC lifetime ceiling does not promise access to the remaining amount. A successful manual transfer does not automatically clear the hold; a supported confirmed reconciliation path is a separate implementation gate.

## Maintenance, privacy and restore

Schema13 maintenance is default disabled and uninstalled. The schema13 runner uses the existing native writer, purges only eligible non-cash exchange content under its separately approved policy, then publishes a schema13 checkpoint. It does not expire ordinary intake/jobs or delete payment holds. Owner-selected cadence/private paths are required; no scheduler or values are selected here. The schema12 CLI deliberately cannot open a schema13 store; use the schema13 wrapper for that reviewed store.

`python3.11 -B -m exchange.payment_requests.maintenance_cli` performs no action by default. Its `--config` and `--execute` procedure uses the exact owner-private configuration format and writer-quiescence requirements in [the non-cash operations guide](../controls/OPERATIONS.md). The explicit configuration is not installed by this change. An active native writer prevents a second terminal writer from opening the store.

Payment requests contain personal business metadata (worker/payee and terms/evidence/acceptance digests). They are owner-only; do not place records, database copies, logs or configuration in public artifacts. This request-only model retains all unresolved principal and minimal retry/obligation history. There is deliberately no blanket payment deletion/expiry. Retention, legal audit needs and eventual resolved-record erasure require owner policy and a reviewed resolution mechanism. Native evidence bytes are not retained here. There is no claim of physical erasure from WAL, backups, screenshots or downloaded copies.

Use `payment_requests.repository` for schema13 `check_store`, `backup_store`, `export_checkpoint` and `restore_store`. Restore requires the **actual current**, quiesced authority store and a separately trusted checkpoint file plus four-field pin, never the backup itself. Complete native business and payment exposure must match current authority after supported non-cash erasure reconciliation. Newer requests, outcomes, holds, native debt or other business changes reject restore before publication. Destination must be new. Lost-source recovery is unsupported; an old copy/checksum cannot prove current erasures or debt. The legacy private admin restore command lacks these required arguments and fails closed; it is not a supported recovery entrypoint for schema13.

The actual13 native recovery hook preserves all native credential-family, policy, execution-approval, standing-grant and authority revocations, financial STOP and `restore_snapshot` gaps. Restored exchange/payment preparation stops, memberships are revoked, original request digests/holds persist and retry keys remain disabled. No credentials/grants are reissued automatically. Exact-source loss, unsupported rollback or failure to publish a checkpoint requires owner reconciliation; do not bypass the fence.

## Stop and rollback

Request `stop` closes preparation immediately and retains every hold/outcome. Host disablement removes the route; neither changes financial STOP or authorizes payment. Revoking owner credentials/membership blocks subsequent preparation, including an upload authenticated earlier. A source mismatch holds the historical request for reconciliation.

Before schema13, roll back source-only review artifacts normally. After schema13, the old schema12 host refuses the store: **there is no in-place downgrade**. Roll back to a compatible schema13 binary with request preparation disabled, keeping current data/holds. A backup restore must pass the full current-source fence and native recovery procedure, including separate intake reconciliation. Do not restore an older backup to erase newer obligations or re-enable authority. Any activation/deployment/rollback of live services requires its own explicit approval.
