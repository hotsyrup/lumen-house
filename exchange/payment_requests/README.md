# Owner payment requests — disabled review slice

This prepares and reserves a payment request after an existing native **paid** job has exact independent owner/buyer/worker assent and owner-accepted delivery. It never signs, broadcasts, sends, settles, grants resources, or enables financial execution. Non-cash exchanges do not become paid work. A principal ceiling is not an award or a wallet balance.

The approved ceilings are **0.10 USDC per job, 1 USDC per America/Los_Angeles calendar day, and 5 USDC lifetime**. The exact job amount comes from its accepted native paid terms. All unresolved requests, including prior-day, failed, unknown and wallet-cancelled outcomes, count against daily and lifetime exposure. Reporting an outcome never releases money or creates a replacement. Fees are separate, unknown and unapproved. Calendar boundaries use the IANA timezone, including 23/25-hour DST days; existing native owner policies retain their own explicit periods.

## Authority and source

`PaymentRequestService` defaults to disabled. Enabling requires an explicitly installed single native owner **and tenant**, a separately migrated schema13 repository, current native credentials and the exact active owner membership with `exchange:admin`. Existing cloud profiles are checked and remain unchanged. If any retained request state already belongs to another tenant of that payer, reinstallation under a different tenant is refused. This single-payer installation boundary prevents a tenant change multiplying the budget. There is no participant, tenant or permission provisioning API here.

Client input for preparation is only `jobId`. The SELECT-only adapter obtains the owner, worker/payee attestation, current paid terms and all three independent assents, complete evidence and exact owner acceptance from the same native database transaction. It requires current terms and buyer/provider attestations, active identities and exact owner/tenant binding. Existing native payment authority, manifests, execution approvals or attempts—including revoked/failed history—hold preparation for reconciliation. No native financial creation, authorization, manifest, dispatch or provider API is invoked.

The opt-in HTTP wrapper derives a request after a successful native owner delivery acceptance. A stopped/full/unavailable derivative returns a redacted request hold while preserving the accepted obligation. Replaying the original native acceptance retries derivation safely. This is an installed-host integration seam, not a running event subscription or scheduler. Requests may also be prepared through the owner commands route. Credential/profile/membership and current source are rechecked on every call. Stale source is displayed as a held historical request; its principal remains reserved.

Native identity verification is **owner attestation**, not independently proven wallet ownership. Native delivery metadata retains a digest/size, not artifact bytes. This code cannot independently check those bytes and reports that limitation. A request stores exact source hashes, identities, payee, amount, asset/network tuple, evidence/acceptance hashes, LA origin day and immutable request digest. It does not certify token contracts, wallet software, balances or network fees.

## Storage and routes

The existing native lifetime writer lease, RLock and `BEGIN IMMEDIATE` transaction cover fresh authentication, tenant/payer checks, source reads, reducer admission and CAS storage. Schema13 adds one bounded state table and two triggers to reviewed schema12; migration is explicit and offline. Normal startup never migrates. Full schema fingerprints are pinned independently. Immutable request/obligation/history and hold fences prevent a self-consistent update from removing exposure, changing origin day or re-enabling recovery retries. Admission reserves real serialized space for all future outcome reports and bounded audit/control operations.

The uninstalled owner namespace is `/api/owner/payment-requests/{tenant}`: GET policy, GET `records[/id]`, POST `commands`. Supported commands are `configure` (retains a review reference for fixed ceilings), `open` (request preparation only), `stop` (requires reason), `prepare` and `report_outcome`. No confirmation, send, release, deletion or settlement endpoint exists. Default-disabled handlers delegate existing native behavior exactly. The Cloudflare passthrough, public storefront and all existing Durable Object bindings remain untouched.

The read-only synthetic mobile/desktop renderer lives under `.github/payment-request-review/`, excluded from the observed Pages upload. Its wallet action remains disabled for every input. **The current native host has no verified mobile wallet confirmation handoff.** This slice honestly stops at a retained request. A future reviewed owner wallet integration must bind exact payer/payee, job/evidence/terms, canonical chain/token, amount and separately approved fees through final owner confirmation. An arbitrary manual wallet transfer cannot provide exactly-once confirmation to this ledger; unknown exposure stays held.
