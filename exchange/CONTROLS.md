# Non-cash exchange controls — source review

This is a default-off production-control candidate for the existing House record service. It is **not deployed, provisioned, or ready for live use**. Payments, wallets, financial workflow creation, actual resource access and automatic fulfillment have no implementation path here. Resource units are owner-defined internal accounting, not money, transferable credits, inventory or a commitment of human time.

The original storefront, discovery skill, three Worker Durable Object exports/bindings, disabled production passthrough, and synthetic demo are unchanged. No second service, database subscription, identity provider or credential system is introduced. The native durable repository is distinct from the Node demo SQLite store; demo records cannot be imported.

## Source and integration boundary

The review branch starts at public `main` commit `f663dec66d4edbb6523d3b770166c949742ba6fe`, the merged PR1. The older Mac storefront checkout contains unrelated changes and was left untouched. The retained release readback identifies Worker version `5522d482-e588-4388-9bdc-7150904c7afe` at 100%; it is dated evidence, not a fresh provider metadata attestation.

The native Python installation supplies `PilotIdentityStore`, `PilotHandler`, `authorize_cloud_command` and `FulfillmentRepository`. Private runtime source, configuration, customer data and release artifacts are deliberately absent from this public repository. Native fixture tests require an explicit local source path and Python 3.10 or later; Python 3.11 was used.

`controls/service.py` requires the identity and state repositories to be the exact same object. For each operation, including get/list and retries, it locks the native repository and starts its existing transaction, revalidates the actual current credential and native role, applies existing cloud-profile restrictions, loads exact tenant membership, checks owner binding and scopes, then commits the reducer state. Request bodies cannot select an actor, tenant membership, owner role or authenticated subject. Existing narrowly scoped cloud invitations gain no exchange access.

Tenant owner and membership identity are immutable. There are no membership or tenant rows initially and no HTTP provisioning operation. A native owner credential alone does not own an arbitrary tenant. Native buyer/provider identities require a separately approved agent membership; native owner identities require the exact tenant-owner binding. Membership deadlines are nullable and are not invented by startup. Existing credential/security expiry checks are preserved.

Before recording new assent, approval or delivery, the adapter also checks both participants' current membership and native account activity in the transaction. Deactivating a participant therefore prevents a new owner reservation from previously captured assent. An assent belongs to the stable principal; rotating its bearer does not erase a valid historical decision. Revoking a credential prevents that credential's further use; revoking membership or the internal resource authorization prevents further exchange authority.

The handler factory is opt-in and defaults to exact existing-host fallback. Importing these modules mounts no routes. The proposed API is under `/api/v1/exchange/{tenant}`: owner policy GET, participant-filtered `/records` GET, exact `/records/{id}` GET and `/commands` POST. It reuses native bearer parsing, unique-key JSON, bounded bodies, upload timeout, rate limits, host/origin guards, no-store responses and error redaction. Evidence export is the same authorized record read; there is no public evidence URL or external fetch.

## Lifecycle and invariants

- New tenant state is stopped with no policy, grants, resources, quotas or offered capabilities. Configuration requires explicit owner limits and is separate from opening the pilot. Synthetic test values are not production recommendations or approvals.
- Terms include a deliverable, acceptance criteria, cancellation conditions, resource identifier and integer units. The canonical SHA-256 binds both participants, tenant/proposal, terms revision, policy revision, disclosure version, purpose/audience/rights, retention and reservation terms. Each participant independently assents with their own authenticated identity, exact current version/hash and explicit sharing consent. An owner cannot supply both assents. Revision invalidates old assents; approval is a separate owner operation.
- A single native transaction commits resource/participant reservations, proposal, audit and idempotency. Owner approval checks both resource capacity and cumulative per-participant limits. Acceptance moves reserved units to consumed units. Completing or deleting a record cannot recycle consumed capacity; policy changes cannot erase it or reduce a limit below recorded use.
- Provider delivery records a bounded description and claimed artifact SHA-256. It does not prove delivery, ownership, security or quality. Only an owner can accept, after an independent assessment bound to the exact delivery revision/hash. No automatic download, verification, grant or payout occurs. A repeated acceptance cannot consume twice.
- Pre-delivery cancellation releases the reservation. Delivered cancellation becomes a dispute and holds units. Reservation timeout is an owner-review hold; it cannot silently free an obligation. Stop/revocation blocks further authority and participant access, including cached evidence. Delivered/disputed obligations remain accounted for until explicit owner resolution. The implemented resolution cancels/releases; it cannot bypass owner acceptance to manufacture completion.
- Command retries bind tenant, subject, key and canonical exact command. A changed body conflicts. Current authorization precedes replay. Deleted/expired content leaves minimized retry tombstones during the bounded retry horizon; retries cannot reconstruct erased content. Clients must retain the original key/body, fetch current state after uncertain outcomes, and never treat an old response as a fresh approval. Keys outside the documented retention/retry horizon provide no perpetual deduplication guarantee.
- Optimistic record versions reject stale concurrent commands. State validation rejects unknown schemas, corrupt terms, audit relationships and accounting rather than repairing away debt. Bounded admission and reserved byte/history headroom keep stop, revoke, resolution and cleanup available under saturation. Hash chains detect inconsistent edits; a privileged writer able to rewrite the database can recompute them. They are not an independent signed audit service.

## Privacy, retention and recovery

Collect only the proposal/terms, native subject references, exact consent, bounded evidence description/digest and owner assessment needed for review. Do not submit secrets, personal contact details, private links, third-party material without rights, or evidence that needs an unimplemented access model. No credential token, wallet, payment payload or evidence file is stored here. Consent permits the specified negotiation/evidence audience and purpose; it grants no resale or training rights.

Owner-defined retention is part of the disclosure. Authorized access runs cleanup. `controls/maintenance.py` supplies a default-disabled in-process runner; the optional owner-terminal module is also inert by default and cannot bypass the native writer lease. Neither installs a task, thread or schedule. Unused tenants retain expired payloads until approved maintenance runs: installation, cadence and private checkpoint custody remain owner decisions. Unresolved delivered/disputed obligations receive a visible retention hold and require owner resolution; they are not silently erased or counted as free capacity. This exception must be approved with the pilot policy. See [operational boundaries](controls/OPERATIONS.md).

Terminal logical deletion removes terms/evidence/content audit and cached responses. Minimal retry hashes remain only through the retry horizon; cumulative resource/grant totals remain to prevent overspend. This is not secure physical erasure. SQLite pages/WAL, snapshots, backups and downloaded copies have separate disposal requirements. Before launch, approve a backup schedule, access policy, retention/deletion process, dispute hold policy and evidence storage rules. A fresh restore must also replay the deletion/consent policy so a pre-deletion backup cannot silently republish erased material.

Logical removal also records a minimal digest erasure receipt in the native transaction. Backup/restore uses native checksum, fingerprint, integrity and writer-lock machinery. Restore requires the complete reviewed native recovery hook, the actual quiesced current source and a separately pinned checkpoint matching that source. It reconciles erasures before publishing a new isolated file, and rejects missing/newer business state or accounting differences. Full native policy/execution/standing revocations, authorities and recovery control gaps are retained alongside exchange STOP and revoked memberships. Consumed accounting and unresolved delivery evidence remain. Missing authority, stale evidence or source loss blocks restore; an old backup alone is never sufficient. Restoring a file grants no permission to reopen it.

## Rollback and remaining blockers

Before migration, abandon the candidate and keep the existing service/version. After migration, prefer a code rollback that understands schema12, keeps the exchange disabled/stopped, preserves the native writer and all accounting/journals, and leaves established House functions mounted. Old schema11 binaries/admin/recovery tools intentionally reject schema12; they cannot be used as a casual rollback. Never overwrite new obligations with a v11 backup. A data restore needs explicit owner approval, reconciliation of every post-backup write and deletion, isolated verification and deliberate re-provisioning.

Resource accounting is scoped to one tenant. The initial pilot must assign each concrete offered resource to one approved tenant; this implementation does not coordinate a resource pool duplicated across tenants. An internal grant is never an automatic tool, file, account or infrastructure permission.

The Cloudflare Worker is not changed by this phase; its retained disabled version remains the release baseline to recheck before any future release. The final native fixture run uses the separately verified no-cutoff intake release source context; its live release was performed by another task. The private host patch must preserve that context, including the absence of undeployed mobile payment routes. This phase performs no upload. Production schema/backup inventory, actual credentials/memberships, owner resource policy, retention runner/backup disposal and controlled live E2E remain unverified or unapproved. Unknown referral/financial records remain unknown obligations until independently reconciled.

See `controls/README.md` for exact local checks and evidence limits. Reviewable source, tests and a draft PR are deliverables; green fixtures are not live readiness.
